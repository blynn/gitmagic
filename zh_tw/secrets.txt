== 揭開面紗 ==

我們揭開Git神秘面紗，往裡瞧瞧它是如何創造奇蹟的。我會跳過細節，若要更深入的瞭解Git
工作原理，可參見 http://schacon.github.com/git/user-manual.html[ 用
戶手冊]。

=== 大象無形 ===

Git怎麼這麼謙遜寡言呢？除了偶爾提交和合並外，你可以如常工作，就像不知道版本控
制系統存在一樣。那就是，直到你需要它，並且感到時間合適的時候以外，Git都只是默
默在後臺看顧著你。

其他版本控制系統強迫你與繁文縟節和官僚主義不斷鬥爭。檔案的許可權可能是隻讀的，
除非你明確地告訴中心伺服器哪些檔案你打算編輯。即使最基本的命令，隨著使用者數目
的增多，也會慢的像爬一樣。中心伺服器可能正跟蹤什麼人，什麼時候check out了什麼
程式碼。當網路連線斷了的時候，你就遭殃了。開發人員不斷地與這些版本控制系統的種
種限制作鬥爭。一旦網路或中心伺服器癱瘓，工作就嘎然而止。

與之相反，Git簡單地在你工作目錄下的`.git`目錄儲存你專案的歷史。這是你自己的歷
史複製，因此你可以保持離線，直到你想和他人溝通為止。你擁有你的檔案命運完全的
控制權，因為Git可以輕易在任何時候從`.git`重建一個曾經儲存過的狀態。

=== 資料完整性 ===

很多人把加密和保持資訊機密關聯起來，但一個同等重要的目標是保證資訊安全。合理
使用雜湊加密功能可以防止無意或有意的資料損壞行為。

一個SHA1雜湊值可被認為是一個唯一的160位ID數，用它可以唯一標識你一生中遇到的每
個位元組串。 實際上不止如此：每個位元組串可供任何人用好多輩子。

對一個檔案而言，其整體內容的雜湊值可以被看作這個檔案的唯一標識ID數。

因為一個SHA1雜湊值本身也是一個位元組串，我們可以雜湊包括其他雜湊值的位元組串。這
個簡單的觀察出奇地有用：檢視“雜湊鏈”。我們之後會看Git如何利用這一點來高效地
保證資料完整性。

簡言之，Git把資料儲存在`.git/objects`子目錄，那裡看不到正常檔名，相反你只
看到ID。通過用ID作為檔名，加上一些檔案鎖和時間戳技巧，Git把任意一個原始的文
件系統轉化為一個高效而穩定的資料庫。

=== 智慧 ===

Git是如何知道你重新命名了一個檔案，即使你從來沒有明確提及這個事實？當然，你或許
是運行了 *git mv* ，但這個命令和 *git add* 緊隨 *git rm* 是完全一樣的。

Git啟發式地找出相連版本之間的重新命名和複製。實際上，它能檢測檔案之間程式碼塊的移
動或複製！儘管它不能覆蓋所有的情況，但它已經做的很好了，並且這個功能也總在改
進中。如果它在你那兒不工作的話，可以嘗試開啟開銷更高的複製檢測選項，並考慮升
級。

=== 索引 ===

對每個加入庫中管理的檔案，Git都會在一個名為“index”的檔案裡記錄統計資訊，諸如
大小，建立時間和最後修改時間。為了確定檔案是否被更改，Git會將當前統計資訊同那
些在索引裡的統計資訊對比。如果一致，那Git就跳過該檔案。

因為統計資訊的呼叫比讀檔案內容快的很多，如果你僅僅編輯了少數幾個檔案，Git幾乎
不需要什麼時間就能更新他們的統計資訊。

我們前面講過索引是一箇中轉區。為什麼一堆檔案的統計資料是一箇中轉區？因為新增
命令將檔案放到Git的資料庫並更新它們的統計資訊，而無引數的提交命令將只基於統計
資訊和已經在資料庫裡的檔案來建立一個全新的提交。

=== Git的源起 ===

這個 http://lkml.org/lkml/2005/4/6/121[ Linux核心郵件列表帖子] 描述了導致
Git誕生的一系列事件。對Git史學家而言，整個討論線是一個令人著迷的歷史探究過程。

=== 物件資料庫 ===

你資料的每個版本都儲存在“物件資料庫”裡，其位於子目錄`.git/objects`內；其他位
於`.git/`的較少資料：索引，分支名，標籤，配置選項，日誌，頭提交的當前位置等。
物件資料庫樸素而優雅，是Git的力量之源。

`.git/objects`裡的每個檔案是一個物件。有3種物件跟我們有關：“blob”物件，
“tree”物件，和“commit”物件。

=== Blob物件 ===

首先來一個小把戲。選擇一個檔名，任意檔名。在一個空目錄：

 $ echo sweet > YOUR_FILENAME
 $ git init
 $ git add .
 $ find .git/objects -type f

你將看到 +.git/objects/aa/823728ea7d592acc69b36875a482cdf3fd5c8d+ 。

我如何在不知道檔名的情況下知道這個？這是因為以下內容的SHA1雜湊值：

 "blob" SP "6" NUL "sweet" LF

是 aa823728ea7d592acc69b36875a482cdf3fd5c8d，這裡SP是一個空格，NUL是一
個0位元組，LF是一個換行符。你可以驗證這一點，鍵入：

  $ printf "blob 6\000sweet\n" | sha1sum

Git基於“內容定址”：檔案並不按它們的檔名儲存，而是按它們包含內容的雜湊值，
在一個叫“blob物件”的檔案裡。我們可以把檔案內容的雜湊值看作一個唯一ID，這樣
在某種意義上我們通過他們內容放置檔案。開始的“blob 6”只是一個包含物件型別與
其長度的頭；它簡化了內部儲存。

這樣我可以輕易預言你所看到的輸出：檔名是無關的：只有裡面的內容被用作構
建blob物件。

你可能想知道對相同的檔案會發生什麼。試圖填加一個你檔案的複製，什麼檔名都行。
在 +.git/objects+ 的內容保持不變，不管你加了多少。Git都只儲存一次資料。

順便說一句，在 +.git/objects+ 裡的檔案用zlib壓縮，因此你不應該直接檢視他們。
可以通過http://www.zlib.net/zpipe.c[zpipe -d] 管道， 或者鍵入：

 $ git cat-file -p aa823728ea7d592acc69b36875a482cdf3fd5c8d

這樣可以漂亮地打印出給定的物件。注意，上面的cat-file命令中，aa是目錄名。

=== Tree物件 ===

但檔名在哪？它們必定在某個階段儲存在某個地方。Git在提交時得到檔名：

 $ git commit  # 輸入一些訊息。
 $ find .git/objects -type f

你應看到3個物件。這次我不能告訴你這兩個新檔案是什麼，因為它部分依賴你選擇的文
件名。我繼續進行，假設你選了``rose''。如果你沒有，你可以重寫歷史以讓它看起來
像似你做了：

 $ git filter-branch --tree-filter 'mv YOUR_FILENAME rose'
 $ find .git/objects -type f

現在你應看到檔案 +.git/objects/05/b217bb859794d08bb9e4f7f04cbda4b207fbe9+ ，因
為這是以下內容的SHA1雜湊值：

 "tree" SP "32" NUL "100644 rose" NUL 0xaa823728ea7d592acc69b36875a482cdf3fd5c8d

通過鍵入以下命令來檢查這個檔案真的包含上面內容：

 $ echo 05b217bb859794d08bb9e4f7f04cbda4b207fbe9 | git cat-file --batch

使用zpipe，驗證雜湊值是容易的：

 $ zpipe -d < .git/objects/05/b217bb859794d08bb9e4f7f04cbda4b207fbe9 | sha1sum

與檢視檔案相比，雜湊值驗證更輕巧一些，因為其輸出不包含原始未壓縮檔案。

這裡的輸出是一個“tree”物件：一組包含檔案型別，檔名和雜湊值的資料。在我們的例
子裡，檔案型別是100644，這意味著“rose”是一個一般檔案，並且雜湊值指blob物件，
包含“rose”的內容。其他可能檔案型別有可執行，連結或者目錄。在最後一個例子裡，
雜湊值指向一個tree物件。

在一些過渡性的分支，你會有一些你不再需要的老的物件，儘管在寬限過期之後，它們
會被自動清除，現在我們還是將其刪除，以使我們比較容易跟上這個示範的例子。

 $ rm -r .git/refs/original
 $ git reflog expire --expire=now --all
 $ git prune

在真實專案裡你通常應該避免像這樣的命令，因為你在破壞備份。如果你期望一個乾淨
的倉庫，通常最好做一個新的克隆。還有，直接操作 +.git+ 時一定要小心：如果
Git命令同時也在執行會怎樣，或者突然停電？一般，引用應由 *git update-ref -d*
刪除，儘管通常手工刪除 +refs/original+ 也是安全的。

=== Commit物件 ===

我們已經解釋了三個物件中的兩個。第三個是“commit”物件。其內容依賴於提交訊息
以及其建立的日期和時間。為滿足這裡我們所需的，我們不得不調整一下：

 $ git commit --amend -m Shakespeare  # 改提交訊息
 $ git filter-branch --env-filter 'export
     GIT_AUTHOR_DATE="Fri 13 Feb 2009 15:31:30 -0800"
     GIT_AUTHOR_NAME="Alice"
     GIT_AUTHOR_EMAIL="alice@example.com"
     GIT_COMMITTER_DATE="Fri, 13 Feb 2009 15:31:30 -0800"
     GIT_COMMITTER_NAME="Bob"
     GIT_COMMITTER_EMAIL="bob@example.com"'  # Rig timestamps and authors.
 $ find .git/objects -type f

你現在應看到 +.git/objects/49/993fe130c4b3bf24857a15d7969c396b7bc187+ 是下列
內容的SHA1雜湊值：

 "commit 158" NUL
 "tree 05b217bb859794d08bb9e4f7f04cbda4b207fbe9" LF
 "author Alice <alice@example.com> 1234567890 -0800" LF
 "committer Bob <bob@example.com> 1234567890 -0800" LF
 LF
 "Shakespeare" LF

和前面一樣，你可以執行zpipe或者cat-file來自己看。

這是第一個提交，因此沒有父提交，但之後的提交將總有至少一行，指定一個父提交。

=== 沒那麼神 ===

Git的秘密似乎太簡單。看起來似乎你可以整合幾個shell指令碼，加幾行C程式碼來弄起來，
也就幾個小時的事：一個基本檔案操作和SHA1雜湊化的混雜，用鎖檔案裝飾一下，檔案
同步保證健壯性。實際上，這準確描述了Git的最早期版本。儘管如此，除了巧妙地打包
以節省空間，巧妙地索引以省時間，我們現在知道Git如何靈巧地改造檔案系統，使其成
為一個完美的版本控制資料庫。

例如，如果物件資料庫裡的任何一個檔案由於硬碟錯誤損毀，那麼其雜湊值將不再匹配，
這個錯誤會報告給我們。通過雜湊化其他物件的雜湊值，我們在所有層面維護資料完整
性。Commit物件是原子性的，也就是說，一個提交永遠不會部分地記錄變更：在我們已經
儲存所有關於tree物件，blob物件和父commit物件之後，我們才可以計算提交的的雜湊
值並將其儲存在資料庫，物件資料庫不受諸如停電之類的意外中斷影響。

我們打敗了即使是最狡猾的對手。假設有人試圖悄悄修改一個專案裡一個遠古版本檔案的
內容，為使物件據庫看起來健康，他們也必須修改相應blob物件的雜湊值，既然它現在
是一個不同的位元組串。這意味著他們將不得不引用這個檔案的tree物件的雜湊值，並反
過來改變所有與這個tree相關的commit物件的雜湊值，還要加上這些提交所有後裔的哈
希值。這暗示官方head的雜湊值與這個壞倉庫不同。通過跟蹤不匹配雜湊值線索，我
們可以查明殘缺檔案，以及第一個被破壞的提交。

總之，只要20個位元組代表最後一次的提交是安全的，我們就將不可能篡改一個Git倉庫。

那麼Git的著名功能怎樣實現的呢？分支？合併？標籤？這些都是單純的細節。當前head保
存在檔案+.git /HEAD+ ，其中包含了一個commit物件的雜湊值。該雜湊值在執行提交
以及其他命令時更新。分支幾乎一樣：它們是儲存在 +.git/refs/heads+ 的檔案。標籤
也是：它們住在 +.git/refs/tags+ ，但它們由一套不同的命令更新。
